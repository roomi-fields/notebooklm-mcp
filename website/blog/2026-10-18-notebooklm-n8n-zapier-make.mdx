Zapier's NotebookLM page says the integration has not been built, and Make has
no module either. n8n is now the exception: there is a community node for
Gemini Notebook — the one we publish — so there you get native operations
instead of a workaround.

For Zapier and Make the honest state is unchanged, and the fix predates the
node: a local HTTP endpoint your workflow calls like any other API, to automate
the part people want — asking a question and getting a citation-backed answer
into the workflow. This post covers both paths.

{/* truncate */}

> **A note on the name.** Google renamed NotebookLM to **Gemini Notebook** in
> July 2026. It is the same product, old links redirect, and everything below
> applies to both — the two names are used interchangeably here because that
> is how people still search for it.

## Why do the big platforms still ship nothing?

Because a connector needs an API with a key, and the consumer Gemini Notebook
has neither. Google's documented API is the enterprise one, behind a Cloud
project and an administrator — a connector built on it would serve only the
users who could already script it.

Our server supplies the missing API: it holds your Google session and exposes
the operations over plain HTTP with a token. For n8n we went one step further
and packaged those operations as a community node, so there you install it and
pick an operation. Zapier and Make get the HTTP route below.

## What do the two paths look like?

**n8n** — install the community node and choose an operation; the question, the
answer and its citations are fields, not JSON you parse by hand. The worked
flow is in [the n8n guide](/notebooklm-n8n).

**Zapier and Make** — run the server on a machine the workflow can reach, then
use their generic webhook or HTTP action: POST the question, read the answer
and its citations out of the response, pass them to the next step. The
[Zapier recipe](/notebooklm-zapier-webhooks) walks through one request field by
field.

Either way the answer arrives as data, so it can go to a sheet, a Slack
message, a database row or a document, like anything else in the workflow.

## Where does the server have to run?

Somewhere the workflow engine can reach, which is the real constraint.

Self-hosted n8n on the same machine is the simple case: the server stays on
loopback and nothing is exposed. Cloud-hosted n8n, Zapier or Make cannot reach
your laptop, so you need the server on a host they can see — and at that point
you are exposing an endpoint that holds a live Google session.

If you do that, set a token. Our server refuses to start on a public interface
without one, which is deliberate: the failure is louder than a leak.

## What is worth automating this way?

The jobs where the answer is one step of several. A weekly digest that asks
each notebook what changed. A support flow that answers from internal
documentation with the passage attached. A research pipeline that files each
answer with its citations into a table.

The pattern that pays best is answer-once-then-store. Usage is a compute
allowance now, refreshed every five hours, so a workflow that re-asks the same
question every run is spending for nothing.

## When is this the wrong design?

- **When latency matters.** An answer takes seconds, not milliseconds. Do not
  put it in front of a user who is waiting.
- **When the workflow must never stall.** The allowance can run out mid-run.
- **When you would be exposing the server to the public internet just to reach
  a cloud workflow tool.** Weigh that against moving the workflow instead.
- **When a plain Gemini API call would do.** If you do not need grounding in
  your own documents, you do not need any of this.

## Trying this one

```bash
git clone https://github.com/roomi-fields/notebooklm-mcp.git
cd notebooklm-mcp && npm install && npm run build
npx -y -p @roomi-fields/notebooklm-mcp notebooklm-mcp-setup-auth
HTTP_PORT=3000 node dist/http-wrapper.js
```

Node 22 or newer. The worked n8n flow is in
[the n8n guide](/notebooklm-n8n); the full endpoint list is in
[the API reference](/notebooklm-rest-api).
